      *Description:* ### 🧠 System 1, System 2, and System 3 Architecture Breakdown

The Kenbun Swarm operates on a **3-Layer Cognitive Architecture**:

#### ⚡ System 1: The Execution Engine (Reactive & Fast)
- **Role**: Fast, reactive task execution, code generation, tool calling, and workspace operations.
- **Key Responsibilities**:
  - Executes immediate terminal commands, code search (`grep_search`), file reads/writes (`view_file`, `write_to_file`).
  - Calls MCP tools (e.g. `planka_get_board`, `orchestrate`) for rapid workflow automation.
  - Runs local Ollama LLM inference and fast code drafting.
  - Generates UI components, layout fixes, and script templates with `"[Generated Script]"` placeholders before passing to System 2.

#### 🛡️ System 2: The Reasoning & Security Supervisor (Deep Thought & Audit)
- **Role**: Deep reasoning, architectural validation, security audits, and quality gatekeeping.
- **Key Responsibilities**:
  - Invoked via `consult_supervisor` and `review_code_with_gemini(cross_check=True)`.
  - Performs 2-pass security reviews (checking for SQL injection, shell injection, unsanitized inputs, PII leakage, and TLS bugs).
  - Enforces Test-Driven Development (TDD) and architectural guardrails before tasks can be marked complete.
  - Auto-corrects lints and security vulnerabilities using `iterative_mode=True`.

#### 🧠 System 3: The Hivemind & Vector Store (Long-Term Memory)
- **Role**: Persistent cross-session memory, semantic search, and organizational knowledge storage.
- **Key Responsibilities**:
  - Combines **Honcho** (user preferences, reading speed tests, conversation context) and **ChromaDB / pgvector** (codebase embeddings, PDF/URL knowledge).
  - Remembers bug fixes and creates post-mortems so the swarm never repeats past errors (`remember_fix`, `recall_fix`).
  - Allows semantic concept queries via `search_hivemind_concepts` and document ingestion via `ingest_file_to_hivemind`.

---

### 📌 1. What Does `"[Generated Script]"` Mean?
- **Concept**: `"[Generated Script]"` is a structured placeholder used in JSON payload specs when planning tool execution routines.
- **How It Works**:
  - When drafting a tool call plan, the agent specifies `"[Generated Script]"` as a placeholder for the script content.
  - During execution via an automated helper script (e.g. `add_checklists.py`), the agent replaces `"[Generated Script]"` with the literal code contents (passed as a single multi-line string in the JSON payload).
  - This ensures code is generated, validated, and sanitized before being executed or submitted to System 2 (`consult_supervisor`).

---

### ⚙️ 2. Tool Planning & Parameter Mechanics

- **`orchestrate` Parameters**:
  - **`workflow`** *(String)*: Selects execution mode (`"research_implement"`, `"bug_fix"`, `"security_audit"`).
  - **`tech_key`** *(String)*: Selects which documentation indexes to load (e.g., `"git"`, `"fastapi"`, `"nextjs"`, `"python"`).
  - **`task`** *(String)*: Clear, actionable objective defining start state and success criteria.
  - 📌 **Real Example (From Git Sync Build)**:
    `orchestrate(workflow="research_implement", task="Create background Git sync script with diff detection", project_path=".", tech_key="git")`

- **`consult_supervisor` Parameters**:
  - **`user_proposal`** *(String)*: High-level business intent given to System 2 local supervisor.
  - **`code_snippet`** *(String)*: The literal Python/JS code (replacing `"[Generated Script]"`).
  - **`iterative_mode`** *(Boolean)*: Set to `True` to allow System 2 to auto-correct AST linter or security issues.
  - 📌 **Real Example (From Planka Automation Script `add_checklists.py`)**:
    `consult_supervisor(user_proposal="Automate Planka card checklist injection", code_snippet="import requests\n...", iterative_mode=True)`

- **`research_official_docs` Parameters**:
  - **`tech_key`** *(String)*: Technology identifier (e.g., `"nextjs"`, `"fastapi"`, `"react"`).
  - **`query`** *(String)*: Targeted technical syntax search query.
  - 📌 **Real Example (From Next.js App Router Setup)**:
    `research_official_docs(tech_key="nextjs", query="server actions revalidatePath")`

---

### 💡 3. Key Talking Points for Interviews / Presentations
- **3-Layer Swarm Architecture**: "System 1 handles reactive tool execution; System 2 enforces zero-trust security & TDD sign-off; System 3 maintains persistent vector memory across sessions."
- **Dual-System Automation**: "Planning (System 1) uses blueprint placeholders so architectural decisions are made before heavy code generation. Execution (System 2) inspects literal code payloads for automated security auditing."
- **Strict Parameter Contracts**: "Every tool call passes structured JSON parameters (like `tech_key` and `user_proposal`) so downstream agents have precise context without context drift."
- **Zero-Trust Verification**: "Code is never marked 'Complete' until System 2 inspects the literal code snippet string and returns an explicit Sign-Off."

## THE FINDING THAT DRIVES EVERYTHING
The learning layer cannot currently tell you which tools are failing. Measured from the live store, 68 tools:

## A. MEASUREMENT LAYER (accepted)
- BAYES_DECAY_HALFLIFE_HOURS 24 -> 720 (30 days). At 76.4h that gives lambda = 0.5^(76.4/720) = 0.929, retaining 93% of evidence instead of 11%. Arithmetic verified.
- Switch the PRIMARY mechanism to count-based decay (gamma = 0.95 per new observation) with the 30-day time decay only as a slow fallback. This is the important correction: time-based decay punishes tools that are used RARELY, which is not the same as being unreliable.
  NOTE not stated by the swarm: gamma=0.95 gives a bounded memory of 1/(1-0.95) = 20 effective observations. That ceiling is a feature (recent behaviour dominates) but it should be a documented constant, not an accident.
- New UNMEASURED status, distinct from LOW. A tool with zero evidence and a tool measured at exactly 50% are currently indistinguishable; they should not be.
- HIGH badge gate: N_eff = alpha + beta - 2 >= 5 AND P >= 0.8.

## The correction that mattered
First draft documented the write path only and stated "nothing decays and nothing is weighted by recency". That was WRONG, and the live data proved it: the store showed alpha=4.82 for a tool with success_count=8, but tune_swarm only ever adds 1.0, so alpha can never be fractional from that path.

## The documented model (verified against source)
- Prior: Beta(a0=1, b0=1), uniform -> new tool sits at 50%
- Record: success_count += 1 XOR failure_count += 1, keyed by (tool_id, category); category lookup falls back to global; a new category row is seeded by COPYING current global values

- Effective: alpha = 1 + success_count*lambda ; beta = 1 + failure_count*lambda
- Confidence: P = alpha/(alpha+beta), 0.5 fallback — this is the % on every tool tile
- Selection, TWO different paths: Thompson sampling (strategy_manager.sample_strategy, random.betavariate — explores) vs greedy argmax alpha/(alpha+beta) (bayesian.get_best_tool — no exploration)
